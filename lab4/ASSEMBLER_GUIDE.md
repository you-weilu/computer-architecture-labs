# Writing Custom Test Programs with `rv32asm.py`

In addition to the 56 provided public tests (which come with pre-built `.trace` files for `tracediff.py`), you can write your own RV32I assembly programs (`.s` files) and assemble them into `mem_in.hex` using `rv32asm.py`.

By design, **no golden-trace simulator is provided for custom programs** (`tracediff.py` is only used with the 56 provided tests in `tests/golden/`). When you write your own test program, **you calculate the expected outputs yourself**, run the program on your Verilog processor, and verify that your processor produced the right results by reading:
1. **`regs_out.hex`** — the final values of all 32 registers (`x0`–`x31`) dumped when your processor halts.
2. **`mem_out.hex`** — the final contents of the 16 KiB memory array (`0x0000`–`0x3fff`).
3. **`trace.txt` & `single.vcd`** — the cycle-by-cycle log and waveforms produced by your processor during simulation.

---

## 1. End-to-End Workflow

### Step 1: Write an Assembly File (`my_test.s`)
Create a plain-text `.s` file ending with `ecall` (which tells your processor to assert `halt = 1`):

```asm
# my_test.s — Basic arithmetic check
    addi x1, x0, 15       # x1 = 15 (0x0000000f)
    addi x2, x0, -4       # x2 = -4 (0xfffffffc)
    add  x3, x1, x2       # x3 = 15 + (-4) = 11 (0x0000000b)
    sub  x4, x1, x2       # x4 = 15 - (-4) = 19 (0x00000013)
    ecall                 # halt at PC = 0x00000010
```

### Step 2: Assemble into `mem_in.hex`
Run `rv32asm.py` with `-l` to display the assembled addresses and 32-bit machine-code words alongside your source lines:

```bash
python3 rv32asm.py my_test.s -o mem_in.hex -l
```

Output:
```text
Address     Encoding     Line  Source
----------------------------------------------------------------
0x00000000  0x00f00093      2  addi x1, x0, 15
0x00000004  0xffc00113      3  addi x2, x0, -4
0x00000008  0x002081b3      4  add  x3, x1, x2
0x0000000c  0x40208233      5  sub  x4, x1, x2
0x00000010  0x00000073      6  ecall
Assembled 'my_test.s' -> 'mem_in.hex' (20 bytes, 5 words).
```

### Step 3: Compile and Run Your Processor
When `lab3_tb.v` runs without `+MEM_IN=...`, it automatically loads `mem_in.hex` and `regs_in.hex` (which initializes all 32 registers to `00000000`):

```bash
iverilog -o single <group>_lab3.v lab3_tb.v
vvp single
```

When your processor asserts `halt`, the testbench writes **`regs_out.hex`**, **`mem_out.hex`**, **`trace.txt`**, and **`single.vcd`**.

## 2. How to Read `regs_out.hex`

`regs_out.hex` is generated by Icarus Verilog's `$writememh` system task. It contains `//` comment lines (such as `// 0x00000000` on Icarus Verilog 11.0 on Wilkinson, or header comments on newer versions) along with **32 lines of 8-digit hexadecimal values** corresponding to `x0` through `x31` in order:

```text
// 0x00000000
00000000
0000000f
fffffffc
0000000b
00000013
00000000
...
```

### Tip: Number the Registers Automatically (`x0`–`x31`)
Use `grep -v '^//' regs_out.hex | nl -v 0` (or `awk`) in the terminal to print the register index right next to each value:

```bash
grep -v '^//' regs_out.hex | awk '{printf "x%-2d = 0x%s\n", NR-1, $1}' | head -n 8
```

Output for `my_test.s`:
```text
x0  = 0x00000000
x1  = 0x0000000f   <-- 15
x2  = 0xfffffffc   <-- -4 (two's complement)
x3  = 0x0000000b   <-- 11
x4  = 0x00000013   <-- 19
x5  = 0x00000000
x6  = 0x00000000
x7  = 0x00000000
```

You can also inspect `trace.txt` to see each instruction's register write in execution order:
```text
1 pc=00000000 inst=00f00093 rd=x1:0000000f
2 pc=00000004 inst=ffc00113 rd=x2:fffffffc
3 pc=00000008 inst=002081b3 rd=x3:0000000b
4 pc=0000000c inst=40208233 rd=x4:00000013
HALT pc=00000010 inst=00000073
```

## 3. Examples of Designing Self-Checking Tests

Because you are calculating the expected outputs yourself, keep each custom test focused on one behavior and store intermediate results in distinct registers (`x1`, `x2`, `x3`, ...) so none of your results overwrite each other before `regs_out.hex` is dumped.

### Example A: Testing Signed vs. Unsigned Comparisons and Shifts

Suppose you want to verify that your ALU distinguishes negative signed numbers from large unsigned numbers on `slt`, `sltu`, `srai`, and `srli`.

1. **Choose inputs with a `1` in bit 31:**
   Let `x1 = -16` (`0xfffffff0`) and `x2 = 8` (`0x00000008`).
2. **Work out the expected values by hand:**
   - `slt x3, x1, x2` (signed: `-16 < 8` is true) $\rightarrow$ `x3 = 0x00000001`
   - `sltu x4, x1, x2` (unsigned: `0xfffffff0 < 8` is false) $\rightarrow$ `x4 = 0x00000000`
   - `srai x5, x1, 2` (arithmetic right shift of `-16` by 2, sign-filling bits 31:30 with `1`) $\rightarrow$ `x5 = -4 = 0xfffffffc`
   - `srli x6, x1, 2` (logical right shift of `0xfffffff0` by 2, zero-filling bits 31:30 with `0`) $\rightarrow$ `x6 = 0x3ffffffc`
3. **Write `shift_cmp.s`:**
   ```asm
       addi x1, x0, -16      # x1 = 0xfffffff0
       addi x2, x0, 8        # x2 = 0x00000008
       slt  x3, x1, x2       # expect x3 = 0x00000001
       sltu x4, x1, x2       # expect x4 = 0x00000000
       srai x5, x1, 2        # expect x5 = 0xfffffffc
       srli x6, x1, 2        # expect x6 = 0x3ffffffc
       ecall
   ```
4. **Assemble, run, and check `x1`–`x6` in `regs_out.hex`:**
   ```bash
   python3 rv32asm.py shift_cmp.s -o mem_in.hex
   iverilog -o single <group>_lab3.v lab3_tb.v && vvp single
   grep -v '^//' regs_out.hex | awk 'NR<=7 {printf "x%-2d = 0x%s\n", NR-1, $1}'
   ```
   Expected output:
   ```text
   x0  = 0x00000000
   x1  = 0xfffffff0
   x2  = 0x00000008
   x3  = 0x00000001
   x4  = 0x00000000
   x5  = 0xfffffffc
   x6  = 0x3ffffffc
   ```

### Example B: Testing Byte/Halfword Loads, Sign Extension, and `.data`

In RV32I memory (little-endian), storing the 32-bit word `0x80ff7f81` at address `0x00001000` places bytes in memory as:
- `Mem[0x1000] = 0x81` (bit 7 is `1`, so `lb` sign-extends to `0xffffff81`, while `lbu` zero-extends to `0x00000081`)
- `Mem[0x1001] = 0x7f` (bit 7 is `0`, so both `lb` and `lbu` produce `0x0000007f`)
- Halfword at `0x1000` (`Mem[0x1001:0x1000]`) is `0x7f81` (bit 15 is `0`, so `lh` and `lhu` both give `0x00007f81`)
- Halfword at `0x1002` (`Mem[0x1003:0x1002]`) is `0x80ff` (bit 15 is `1`, so `lh` gives `0xffff80ff` and `lhu` gives `0x000080ff`)

You can initialize `.data` at `0x00001000` directly in your `.s` file:

```asm
# load_ext.s — Test byte and halfword sign/zero extension
.text
    la   x1, test_word    # x1 = 0x00001000 (use --milestone-a if lui/auipc not built yet)
    lw   x2, 0(x1)        # expect x2 = 0x80ff7f81
    lb   x3, 0(x1)        # expect x3 = 0xffffff81 (signed byte 0x81)
    lbu  x4, 0(x1)        # expect x4 = 0x00000081 (unsigned byte 0x81)
    lb   x5, 1(x1)        # expect x5 = 0x0000007f (signed byte 0x7f)
    lh   x6, 2(x1)        # expect x6 = 0xffff80ff (signed halfword 0x80ff)
    lhu  x7, 2(x1)        # expect x7 = 0x000080ff (unsigned halfword 0x80ff)
    ecall

.data
test_word:
    .word 0x80ff7f81
```

> **Note for Milestone A:** Before you implement `lui` and `auipc` in Milestone B, pass `--milestone-a` to `rv32asm.py`:
> ```bash
> python3 rv32asm.py --milestone-a load_ext.s -o mem_in.hex
> ```
> This expands `la` and `li` using only Milestone A instructions (`addi` and `slli`).

### Example C: Testing Taken vs. Untaken Branches

To verify branch conditions (`beq`, `bne`, `blt`, `bge`, `bltu`, `bgeu`), write a distinct "canary" constant into a register on the fall-through path and another constant at the branch target:

```asm
# branch_check.s
    addi x1, x0, -5       # x1 = -5 (0xfffffffb)
    addi x2, x0, 3        # x2 = 3  (0x00000003)

    # 1. Signed blt: -5 < 3 is TRUE (should branch to taken_1, skipping x3 = 99)
    blt  x1, x2, taken_1
    addi x3, x0, 99       # should be skipped!
taken_1:
    addi x4, x0, 1        # expect x3 = 0x00000000, x4 = 0x00000001

    # 2. Unsigned bltu: 0xfffffffb < 3 is FALSE (should NOT branch)
    bltu x1, x2, bad_2
    addi x5, x0, 1        # should execute: expect x5 = 0x00000001
    beq  x0, x0, done
bad_2:
    addi x6, x0, 99       # should be skipped: expect x6 = 0x00000000
done:
    ecall
```

When you inspect `regs_out.hex`:
- If `x3` is `00000063` (`99`), `blt` failed to take the branch.
- If `x6` is `00000063` (`99`), `bltu` mistakenly took the branch.
- If `x3 = 00000000`, `x4 = 00000001`, `x5 = 00000001`, and `x6 = 00000000`, both branches behaved properly.

### Example D: Testing Halt Conditions (Illegal Instructions & Misaligned Accesses)

Your processor must assert `halt = 1` on any illegal/unsupported instruction or misaligned memory access **without** updating registers or memory on the halting cycle, and without executing any subsequent instructions.

To test this:
1. Write a known value to `x1` *before* the halting instruction.
2. Place the halting instruction (using `.word 0xXXXXXXXX` for illegal encodings, or a misaligned load/store).
3. Place a "canary" instruction `addi x2, x0, 99` *after* the halting instruction.

```asm
# my_halt_test.s — Test halting on an R-type instruction with invalid funct7
    addi x1, x0, 42       # 1. Valid: x1 = 0x0000002a
    # Encode an illegal R-type instruction: rd=x3, rs1=x1, rs2=x1, funct3=000, funct7=0000010 (0x02)
    # 0000010_00001_00001_000_00011_0110011 = 0x041081b3
    .word 0x041081b3      # 2. Should HALT here at PC = 0x00000004! (x3 must remain 0)
    addi x2, x0, 99       # 3. Must NEVER execute (x2 must remain 0)
    ecall
```

Check **both** `regs_out.hex` and `trace.txt`:
- In `regs_out.hex`:
  - `x1` must be `0000002a` (instruction 1 retired).
  - `x3` must be `00000000` (the halting instruction at `0x00000004` did **not** write to `rd`).
  - `x2` must be `00000000` (execution stopped at `0x00000004` and never reached `0x00000008`).
- In `trace.txt`:
  ```text
  1 pc=00000000 inst=02a00093 rd=x1:0000002a
  HALT pc=00000004 inst=041081b3
  ```

## 4. Using the `-l` Assembler Listing Option (`rv32asm.py -l`)

Remember that `rv32asm.py` is a **static assembler**, not a simulator: it translates your assembly source into machine code (`mem_in.hex`), but does **not** execute your program or generate a golden `.trace` file for `tracediff.py`.

Instead, the `-l` (`--list`) flag prints a 4-column **assembly listing table** that maps each memory address (`PC`) and 32-bit hex encoding (`inst`) back to the line number in your `.s` file:

```bash
# Print listing to the terminal:
python3 rv32asm.py my_test.s -l

# Or save the listing to a file:
python3 rv32asm.py my_test.s -l my_test.lst
```

Example output:
```text
Address     Encoding     Line  Source
----------------------------------------------------------------
0x00000000  0x00f00093      1  addi x1, x0, 15
0x00000004  0x00001117      2  auipc x2, 0x1       [la x2, test_word]
0x00000008  0xffc10113      2  addi x2, x2, -4     [la x2, test_word]
0x0000000c  0x00112023      3  sw   x1, 0(x2)
0x00000010  0x00000073      4  ecall
0x00001000  0x80ff7f81      7  .word 0x80ff7f81
```

### How to Use the `-l` Listing While Debugging
1. **Cross-referencing `trace.txt` and `single.vcd`:** When you inspect `trace.txt` or view waveforms in GTKWave (`single.vcd`), you see hexadecimal `PC` addresses (`0x00000000`, `0x00000004`, ...) and 32-bit instruction words (`0x00f00093`, ...). The `-l` listing tells you immediately which line of your `.s` file corresponds to each `PC` and `InstOut` value.
2. **Seeing pseudo-instruction expansions:** Pseudo-instructions like `la` and `li` (for large constants) expand into **2 or 3 hardware instructions**. The `-l` listing shows each expanded instruction with `[la ...]` or `[li ...]` next to it so you can see why `PC` advances by 8 or 12 bytes across a single source line.
3. **Verifying `.data` layout:** The listing shows the exact address (`0x00001000`, ...) and hex encoding of every `.word`, `.half`, `.byte`, or `.space` directive in your `.data` section.

## 5. `rv32asm.py` Quick Reference

### Command-Line Options
```bash
python3 rv32asm.py <input.s> [-o mem_in.hex] [-l [listing_file]] [--milestone-a]
```
- `-o <file>`: Output Verilog hex file (default: `mem_in.hex`).
- `-l`: Print address/hex/source listing to stdout (or pass a filename to save it).
- `--milestone-a`: Expand `li` and `la` using only `addi` + `slli` (no `lui` or `auipc`).

### Supported Register Names
- Numbered: `x0`–`x31`
- ABI names: `zero` (`x0`), `ra` (`x1`), `sp` (`x2`), `gp` (`x3`), `tp` (`x4`), `t0`–`t2` (`x5`–`x7`), `s0`/`fp` (`x8`), `s1` (`x9`), `a0`–`a7` (`x10`–`x17`), `s2`–`s11` (`x18`–`x27`), `t3`–`t6` (`x28`–`x31`).

### Supported Pseudo-Instructions
| Pseudo-Instruction | Expansion |
| :--- | :--- |
| `nop` | `addi x0, x0, 0` |
| `mv rd, rs` | `addi rd, rs, 0` |
| `not rd, rs` | `xori rd, rs, -1` |
| `neg rd, rs` | `sub rd, x0, rs` |
| `seqz rd, rs` | `sltiu rd, rs, 1` |
| `snez rd, rs` | `sltu rd, x0, rs` |
| `j label` | `jal x0, label` |
| `jr rs` / `ret` | `jalr x0, 0(rs)` / `jalr x0, 0(x1)` |
| `call label` | `jal x1, label` |
| `beqz rs, label` / `bnez rs, label` | `beq rs, x0, label` / `bne rs, x0, label` |
| `blez rs, label` / `bgez rs, label` | `bge x0, rs, label` / `bge rs, x0, label` |
| `bltz rs, label` / `bgtz rs, label` | `blt rs, x0, label` / `blt x0, rs, label` |
| `bgt rs, rt, label` / `ble rs, rt, label` | `blt rt, rs, label` / `bge rt, rs, label` |
| `bgtu rs, rt, label` / `bleu rs, rt, label` | `bltu rt, rs, label` / `bgeu rt, rs, label` |
| `li rd, imm` | `addi rd, x0, imm` if `-2048 <= imm <= 2047`; else `lui` + `addi` (or `addi`+`slli`+`addi` with `--milestone-a`) |
| `la rd, symbol` | `auipc` + `addi` (or `addi`+`slli`+`addi` with `--milestone-a`) |

### Supported Directives
- `.text` (default start `0x00000000`), `.data` (default start `0x00001000`)
- `.org <addr>` (move current section address to `<addr>`)
- `.align <n>` (align to $2^n$-byte boundary)
- `.word <v1>, <v2>, ...` (32-bit values; valid in both `.text` and `.data`)
- `.half <v1>, ...` (16-bit values), `.byte <v1>, ...` (8-bit values)
- `.space <bytes>` (zero-filled bytes)
- `.equ NAME, EXPR` (define constant symbol)
